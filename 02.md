# Avaliação fase 2 — posicionamento jurídico e docs

**Premissa informada pelo time:** Hymple **não** será empresa brasileira. A intenção é operar a partir de **jurisdição(ões) favorável(is)**.

**Escopo:** o que o site de documentação (e o marketing adjacente) comunica hoje sobre entidade, KYC, custódia, token e governança — e o que isso implica para um projeto que quer parecer internacional e “reg-aware”, não informal.

**Isto não é parecer jurídico.** É avaliação de produto/docs. Estrutura societária, licenças e geoblock exigem advogado local na jurisdição escolhida.

---

## 1. O que o docs diz hoje (e o que não diz)

### Diz com clareza

- É um **exchange híbrido**: order book **off-chain** + settlement **on-chain**.
- **Não é DAO.** Governança é **centralizada no founding team**, com votação on-chain só complementar (fees, rewards, marketing).
- **“No KYC”** é feature de produto, repetida em Introduction, Architecture e Onboarding.
- Onboarding: conectar wallet, **sem e-mail, senha ou conta tradicional**.
- Usuário deposita em um **“Hymple custody smart contract”**; a plataforma alega não ter poder de saque e só liquidar trades assinados pelo usuário.
- Token **HYM**: supply 70M, TGE, public sale, team vesting, staking, airdrops, fee discounts, “decentralized governance”.
- Compliance citado = **OWASP / CIS / NIST** (segurança de software), não VASP, AML ou licença de exchange.

### Não diz (lacuna crítica para a premissa)

- Nome da **entidade legal** que opera o matching engine, o frontend e o site.
- País / registro / número da companhia.
- Qual entidade emite ou distribui o HYM (public sale).
- Terms of Use, Privacy Policy, Risk Disclosure, Token Disclaimer.
- Lista de **jurisdições restritas**.
- Se “no KYC” é absoluto ou vale só fora de mercados regulados.
- Quem é o operador off-chain (a camada que *não* é open-source).
- Endereços de contrato, chain IDs, auditoras nomeadas.
- Relação entre `docs.hymple.com`, `www.hymple.com` e o espelho GitHub Pages.

Para um projeto que **escolhe jurisdição de propósito**, o silêncio não parece “privacy-first”. Parece **projeto ainda sem cara institucional**. Comprador, market maker e listagem levam isso a sério.

## 2. O desenho real vs. o slogan

O docs mistura três verdades ao mesmo tempo:

| Camada | O que é na prática | Como o copy vende |
|---|---|---|
| Matching, API, UI, order management | Off-chain, código **proprietário**, time central | “Hybrid exchange”, performance de CEX |
| Fundos em contrato + saque só pelo user | Escrow / vault on-chain | “Non-custodial”, “not a custodial institution” |
| KYC / conta | Wallet-only | “No KYC”, “no registration” |
| Governança | Time fundador decide | “Transparent”, token com “decentralized governance” |

Isso é um modelo **conhecido** (order-book híbrido com vault). Não é AMM puro nem CEX custodial clássico.

O problema de comunicação:

1. Chamar o contrato de **“custody smart contract”** e o produto de **“non-custodial”** na mesma jornada. O leitor técnico (e o regulador) lê “custody”.
2. Dizer que **não é broker nem instituição custodial** enquanto opera motor de matching centralizado e interface que instrui depósito no vault da marca.
3. Tratar **“no KYC”** como princípio universal, não como política da entidade em mercados onde isso for lícito.

Em jurisdição favorável o modelo *pode* ser enquadrável. O docs atual não ajuda a enquadrar: ele **maximiza o slogan** e **minimiza o operador**.

---

## 3. Por que “não ser empresa BR” não aparece no site — e deveria

Sair do Brasil como sede **não** torna o projeto invisível para:

- usuários residentes em países com regra de VASP / oferta de token;
- banks, market makers e listagens que pedem entity + ToS + restricted list;
- Apple/Google se houver app;
- Cloudflare/GitHub se houver abuse/sanctions;
- a própria narrativa de “exchange”.

O docs hoje é neutro-genérico em inglês, com traços de redação não-nativa e formatação numérica PT (`15.000.000`, `21,4%`). Isso não prova origem BR, mas também **não constrói** uma sede internacional.

O que um docs “jurisdição-first” costuma deixar no ar (sem tutorial de estrutura):

- **Quem** opera o off-chain.
- **Onde** essa entidade está constituída.
- **O que** o produto *não* é (não é banco, não é oferta a US persons, etc.) — quando o counsel aprovar o texto.
- **Onde** o produto *não* está disponível.

Sem isso, “vamos operar em jurisdição favorável” é decisão interna. Externamente o site ainda parece **protocolo sem emissor**.

## 4. Claims que pesam mais fora do Brasil

Não ranquear países aqui. Só mapear o que o *texto atual* deixa exposto, em qualquer sede “crypto-friendly”.

### 4.1 “No KYC” como headline

Repetido como diferencial de UX. Em muita jurisdição favorável ainda existem:

- obrigações de AML / Travel Rule para certos perfis de VASP;
- sanções e listas restritivas;
- geoblock de residentes de mercados hostis;
- KYC *quando* o produto cruza um limiar (fiat on-ramp, custody efetiva, corretagem).

O docs não distingue:

- **sem cadastro tradicional** (verdade de UX); versus
- **sem nenhum controle de elegibilidade** (afirmação legal ampla).

Recomendação de copy (não de compliance): tirar “No KYC” do mesmo nível que “Non-custodial” e “Open-source contracts”. Mover para política da entidade, com ressalva de restrições geográficas.

### 4.2 Hybrid off-chain matching

O matching proprietário + API + “canais HFT / institucionais” é o que mais aproxima o produto de **plataforma de negociação operada**, não de contrato autônomo.

O próprio docs admite: off-chain **não é open-source** (IP + segurança). Isso é legítimo. Também é o pedaço que uma licença, se existir, vai olhar.

Falta uma página só de **Trust model**:

- o que o operador *pode* fazer (priorizar, cancelar, pausar matching, mudar fees off-chain);
- o que *não pode* (sacar o vault);
- o que acontece se o operador sumir (fundos no contrato? orders órfãs?);
- upgrade / pause / admin keys.

Hoje a página de Security fala Zero Trust, SIEM, NGFW, ML contra spoofing — e zero sobre **admin key do vault** e **quem assina o settlement**.

### 4.3 Token HYM (public sale + utility + governance)

Tokenomics descreve:

- public sale no TGE;
- airdrop;
- staking rewards;
- voting;
- desconto de fee;
- team allocation com cliff.

Isso, num docs público sem disclaimer de token, é o segundo maior buraco depois de KYC. Em sede favorável ainda é comum haver:

- documento de oferta / isenção;
- restrição de comprador;
- linguagem de utility vs. expectation of profit.

O docs trata HYM como pilar econômico do ecossistema, com tom de whitepaper de captação. Para um projeto que *escolheu* jurisdição, o whitepaper deveria **separar**:

- spec do protocolo;
- spec do token;
- termos da oferta (fora do docs técnico, ou claramente marcado).

### 4.4 “Hymple is not a DAO” + “decentralized governance” no token

Isso é honesto — e bom. Não finjam ser DAO.

Mas então o site precisa de um bloco **Legal entity & control**:

- empresa(s) do grupo (op, IP, token issuer — se forem separadas);
- o que a comunidade vota de verdade;
- o que o board decide sozinho.

Governança “centralizada e transparente” sem nomear o centro não é transparente.

## 5. Risco de linguagem: custódia

Trecho do onboarding (espelho GitHub):

> “Deposit into the **Custody Contract**”  
> “Funds remain under the user's exclusive control: Hymple cannot withdraw them”

Dois ajustes de produto/docs:

1. Renomear para **Settlement vault / Trading vault / Escrow contract** se o modelo for “user-gated withdraw”. “Custody contract” contradiz “non-custodial architecture”.
2. Explicar o fluxo em um diagrama: wallet → vault → match off-chain → settle on-chain → withdraw.

Sem diagrama, o leitor vê “deposit into Hymple custody” e classifica como CEX com smart contract.

A landing (`hymple.com`) diz “Hymple never holds your funds” e “assets stay in your wallet”. O docs diz que o usuário **deposita no contrato da Hymple** para começar a tradar. Essas duas frases **não podem conviver** sem uma terceira que reconcilie.

## 6. O que o docs deveria ganhar nesta fase (prioridade)

Ordem prática, pensada para sede internacional — não para “parecer brasileiro” nem para “parecer offshore genérico”.

### P0 — existência mínima institucional

1. Página **Legal** (mesmo que curta, counsel-approved):
   - entidade operadora + endereço de registro (quando existir);
   - links ToS, Privacy, Risk, Token notice;
   - restricted jurisdictions (placeholder até o counsel fechar a lista).
2. **Canonical** só em `docs.hymple.com`; espelho GitHub com `noindex`.
3. Footer no docs e no marketing com a razão social, não só “HYMPLE”.

### P0 — corrigir contradições de modelo

4. Glossário único: *non-custodial* vs *vault* vs *operator*.
5. Página **Trust & Failure modes** (o que quebra se o C# matching cair).
6. Alinhar `hymple.com` FAQ com o docs (wallet vs vault).

### P1 — token e oferta

7. Separar “Token spec” de “Token sale”.
8. Disclaimer padrão de whitepaper (não é prospecto, não é oferta em X jurisdições).
9. Identificar o emissor do TGE quando houver entidade.

### P1 — KYC / acesso

10. Trocar headline “No KYC” por política: wallet-native onboarding + eligibility rules.
11. Não prometer acesso mundial. “Available where permitted” é mais coerente com sede escolhida.
12. Não misturar “privacy” com “estamos fora de AML”.

### P2 — credibilidade técnica que também serve ao jurídico

13. Endereços de contrato, explorers, reports de auditoria *nomeados*.
14. Changelog do whitepaper v1.1.
15. Admin roles / timelock descritos como fato, não como folder de segurança genérico.

## 8. Como escrever sem fingir licença que não existe

Tom útil para sede favorável:

- Específico no técnico (vault, matching, signatures).
- Modesto no legal (“the operator is [Entity], incorporated in [Jurisdiction]”).
- Separado no comercial (token sale ≠ docs de arquitetura).
- Honesto no controle (não é DAO; o time opera o engine).

Tom que prejudica justamente a estratégia de jurisdição:

- “No KYC anywhere.”
- “Not a broker / not custodial” sem definir os termos.
- “Compliance with OWASP/NIST” no lugar de política AML da entidade.
- Security theater (SIEM, NGFW, 24/7) sem nomear admin keys.
- Whitepaper com cara de captação e zero risk notice.

Escolher jurisdição favorável é **estratégia de estrutura**. O docs atual ainda é **estratégia de narrativa**. As duas precisam se encontrar no footer, não só no cap table.
